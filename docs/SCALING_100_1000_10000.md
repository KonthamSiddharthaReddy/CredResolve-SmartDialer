# Scaling from 100 to 1,000 to 10,000 Agents: Bottlenecks & Fixes

This document analyzes system bottlenecks, point-of-failure limits, and exact architectural remediations across three orders of magnitude.

---

## 1. Stage 1: 100 Agents (~20 to 50 Calls / Sec)

### Operational Characteristics
- **Agent pool**: 100 active collections agents.
- **Concurrent connected calls**: ~60 to 80.
- **Ringing calls in-flight**: ~30 to 60.
- **Call initiation rate**: ~5 to 15 calls/second.

### What Breaks First?
1. **SQLite Database Locking**:
   - *Why*: SQLite supports only **one single writer** at any instant (`database is locked` error under concurrent HTTP worker threads), even with WAL mode enabled.
2. **Synchronous Provider Webhook Processing**:
   - If webhooks are executed directly inside synchronous database sessions, webhook latency degrades dialer response time.

### How to Fix It
- **Database**: Migrate from SQLite to **PostgreSQL**.
- **WAL Checkpointing**: In PostgreSQL, multi-version concurrency control (MVCC) enables concurrent reads and writes without thread blocking.
- **Connection Pooling**: Deploy `pgbouncer` in transaction pooling mode with pool size ~20.

## 2. Stage 2: 1,000 Agents (~200 to 500 Calls / Sec)

### Operational Characteristics
- **Agent pool**: 1,000 active collections agents across multiple queues.
- **Concurrent connected calls**: ~700 to 850.
- **In-flight ringing calls**: ~200 to 400.
- **Call initiation rate**: ~50 to 120 calls/second.

### What Breaks First?
1. **Row Lock Contention during Agent & Borrower Allocation**:
   - *The Bottleneck*: Multiple worker nodes executing `SELECT ... WHERE status = 'AVAILABLE' LIMIT 1` will collide on the top rows.
   - *Why*: Optimistic concurrency control (OCC with version column) results in **retry thrashing** where 80% of workers fail their update and must re-query.
2. **Database CPU Saturation on State Polling**:
   - Aggregation queries (`COUNT(*) WHERE status = 'AVAILABLE'`) executed on every dialer tick (e.g. 10 times/sec) saturate DB IOPS and buffer cache.
3. **Telecom Carrier Rate Limits (CPS / Calls Per Second)**:
   - Telecom SIP trunks enforce strict CPS caps (e.g. 30 CPS per SIP trunk group). Bursting 80 calls in 500ms results in carrier SIP 503 / 486 responses.

### How to Fix It
1. **PostgreSQL `FOR UPDATE SKIP LOCKED`**:
   Replace optimistic retries with row-level pessimistic locks that bypass already-locked rows:
   ```sql
   SELECT id 
   FROM agents 
   WHERE status = 'AVAILABLE' 
   ORDER BY last_status_change ASC 
   LIMIT 1 
   FOR UPDATE SKIP LOCKED;
   ```
   Workers dequeue distinct available agents in $O(1)$ time with zero contention.
2. **Redis In-Memory State & Counter Caching**:
   - Maintain agent states and active call counters in Redis using Atomic Hashes (`HSET`) and Bitmaps.
   - Pacing decisions query Redis in $< 1\text{ms}$ instead of executing heavy SQL `COUNT` queries on PostgreSQL.
3. **Token Bucket Rate Limiter for Carrier Trunks**:
   - Introduce a local token bucket limiter (e.g. Leaky Bucket / Token Bucket via Redis or Envoy) to smooth call initiation spikes to the exact carrier CPS cap.

## 3. Stage 3: 10,000 Agents (~2,000 to 5,000 Calls / Sec)

### Operational Characteristics
- **Agent pool**: 10,000 active agents across distributed call centers.
- **Concurrent connected calls**: ~7,500 to 8,500.
- **In-flight ringing calls**: ~2,000 to 5,000.
- **Call initiation rate**: ~500 to 1,500 calls/second.
- **Carrier webhook event rate**: ~3,000 to 8,000 events/second.

### What Breaks First?
1. **Single Database Write Bottleneck (I/O & WAL Saturation)**:
   - *Why*: A single primary PostgreSQL database cannot handle 8,000 write transactions per second (call state updates, agent transitions, audit logs) without replication lag exceeding seconds.
2. **Distributed Telephony & Audio Bridge Latency**:
   - *Why*: At 10,000 agents, connecting an answered borrower to an available agent must occur within **$< 1.5$ seconds** (FCC/Ofcom compliance limit). Centralized routing over WAN introduces audio latency and packet loss.
3. **Centralized Safety Controller Serialization**:
   - If a single controller process attempts to evaluate all 10,000 agents globally, lock serialization and network hops make decisions stale before calls are placed.

### How to Fix It
1. **Cell-Based Architecture (Campaign / Queue Sharding)**:
   - Partition the system into autonomous **Cells** (e.g. 500 agents per Cell).
   - Each Cell possesses:
     - Its own Safety Controller instance.
     - Its own Redis cluster and local database partition / tenant DB.
     - Dedicated SIP trunk groups.
   - Failure of Cell 4 has zero impact on the other 19 Cells.
2. **Event-Driven Asynchronous Pipeline via Kafka / Redpanda**:
   - Carrier webhooks publish raw events to a partitioned Kafka topic (`events.telecom.carrier`).
   - Consumer worker pools process transitions in partitioned batches using event sourcing.
   - Calls and agents are partitioned by `campaign_id` or `agent_id` hash, ensuring strict single-partition ordering for each call lifecycle.
3. **Multi-Carrier SIP Trunk Load Balancing & SBC Edge Routers**:
   - Session Border Controllers (SBCs e.g. FreeSWITCH / Asterisk / Kamailio clusters) terminate media locally at geographically distributed points of presence (PoPs).
   - Dynamic carrier routing shifts traffic between carriers (Airtel, Tata, Jio, Twilio, Plivo) based on real-time ASR (Answer-Seizure Ratio) and ALOC (Average Length of Call).
